# 节点库测速

节点库的「测速」由 ConfigFlow 所在机器发起，使用独立的 `configflow-node-probe` 程序读取完整节点配置，通过节点访问测试地址。不要求节点先发布，也不调用正在运行的 Mihomo 控制接口。

## 先在页面测试

1. 打开「共享资源 → 节点库」，确认节点或订阅已添加。
2. 点击单个节点的测速，或顶部「全部测速」。
3. 等待进度完成，检查延迟或具体错误；页面会按批次更新结果。
4. 提示 DNS 返回 Fake-IP 时，在「测速设置」选择 OxiDNS 托管或自定义 DNS，检测解析结果后重新测速。

这项测试使用 ConfigFlow 主机的网络。目标设备的实际选路和延迟请在其 Mihomo 面板查看，两个结果可能不同。

## 结果与限制

- 默认测试地址：`https://www.gstatic.com/generate_204`，发送 HEAD 请求，不跟随重定向。与 Mihomo 面板未指定预期状态码时的行为一致，收到 HTTP 响应即完成延迟探测，不再将非 204 响应误报为连接失败。
- 默认统一延迟：先完成一次请求，再计时第二次请求，复用连接；首连耗时包含代理握手，也保存并可在结果提示中查看。第二次请求连接失败时沿用 Mihomo 的回退计时（从首连开始到第二次失败）；首次请求失败、证书或认证错误以及整体超时仍失败。
- 默认每个节点总超时 5 秒（包含握手及两次请求），每批最多 20 个并发；页面按批次更新真实完成数。HTTP API 单批最多 20 个，其中需要 Sub-Store 转换的 URI/base64 节点最多 5 个，超出明确拒绝，不静默截断；页面自动按此上限分批。JSON/YAML 与订阅缓存节点可直接进入 20 并发探测。转换耗时不计入网络探测的 5 秒超时。
- 测速程序按批次启动，结束后退出；不启用 TUN、DNS 监听或代理入站端口，不要求 root。服务进程内同一时间只运行一批测试。多进程部署的并发限制按进程计算。
- 支持范围跟随锁定的 Mihomo 协议实现版本（见 `backend/node-probe/go.mod`）；未知协议、配置不完整、代理链依赖会显示失败，不回退成 TCP 测试。节点服务器域名默认使用测速机器的系统 DNS，也可单独指定 DNS；系统透明代理或网关仍可能影响路径。
- 支持 IPv6 地址及仅有 AAAA 记录的节点服务器；ConfigFlow 所在主机或容器仍须具备可用的 IPv6 出网和路由。测速 DNS 使用 IPv4 地址不影响查询 AAAA 记录，修改目标设备的 Mihomo IPv6 开关不会改变独立测速进程的设置。
- 测速请求与历史按来源区分：库内节点使用节点 ID，订阅预览使用订阅 ID 与节点名称。不同来源的同名节点分别测试，不共用结果。旧 TCP 及旧版严格 204 判定的结果不再展示；变更测试地址或统一延迟模式也会开始新的历史。

## 部署

新 Docker 镜像内置组件。已有安装需要重建/更新镜像，单独替换 Python 文件不会补齐二进制。自动更新镜像会校验并重建变更的组件，失败保留前一版。

源码部署需要 Go 1.26 或更新版本。在仓库根目录执行：

```sh
(cd backend/node-probe && CGO_ENABLED=0 go build -trimpath -ldflags='-s -w' -o configflow-node-probe .)
```

程序会优先读取 `CONFIGFLOW_NODE_PROBE_BIN`，否则使用镜像内路径、上述源码构建路径或 PATH 中的 `configflow-node-probe`。找不到组件或组件版本不匹配时页面会提示安装/重建方式，不将已有结果覆盖成超时。Python 后端与 worker 必须一同更新（当前 worker 输出协议版本为 4）。

可选环境变量（设置在 ConfigFlow 服务上，重启后生效）：

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `CONFIGFLOW_NODE_PROBE_BIN` | 自动查找 | 独立组件的可执行文件路径 |
| `CONFIGFLOW_NODE_TEST_URL` | `https://www.gstatic.com/generate_204` | 支持 HEAD 的 HTTP/HTTPS 地址；建议 HTTPS |
| `CONFIGFLOW_NODE_TEST_TIMEOUT_MS` | `5000` | 单节点整体超时，范围 500–10000 毫秒 |
| `CONFIGFLOW_NODE_TEST_UNIFIED_DELAY` | `1` | `0` 或 `false` 改为显示首连总耗时 |

测试地址是节点库独立设置，不改变策略组或 Provider 健康检查配置。程序通过标准输入接收节点配置，不将密码放入命令行或持久化测速结果；页面显示归类后的错误，不暴露核心的原始异常。

### 系统 DNS 返回 Fake-IP 时

如果 ConfigFlow 所在机器使用 OxiDNS / Mihomo 提供的 Fake-IP DNS，节点服务器域名也可能被解析成 `198.18.0.0/15` 中的地址。测速请求随后进入透明代理，可能在代理握手或请求阶段断开；这不代表节点本身不可用。测速组件会拒绝这类解析结果，并明确提示 DNS 返回了 Fake-IP。

在 **节点库 → 测速设置** 中选择以下模式。设置对全部配置空间的节点库测速生效，重启后保留。

| 模式 | 行为 |
| --- | --- |
| 系统 DNS | 使用 ConfigFlow 主机或容器的系统 DNS，不主动指定公共 DNS。 |
| OxiDNS 托管 | 在所选设备上创建专用 UDP/TCP DNS 端口，直接转发到指定上游；只有发布成功并从 ConfigFlow 验证返回真实 IP 后，才可启用。 |
| 自定义 DNS | 填写已有 DNS 地址，仅传给独立测速组件，不生成或发布 OxiDNS / Mihomo 配置。 |

自定义 DNS 支持最多 4 个 `IPv4[:端口]`、`https://主机/路径`（DoH）或 `tls://主机[:端口]`（DoT），用逗号或换行分隔。默认端口分别为 53、443、853；DoH 未填路径时使用 `/dns-query`。不接受 URL 凭据、查询参数、片段或 IPv6 上游地址。IPv4 上游仍可返回节点的 AAAA 记录。

域名形式的 DoH/DoT 必须配置引导 DNS（最多 4 个 IPv4[:端口]）；它只负责解析加密 DNS 服务的主机名，不会自动退回系统 DNS。引导结果为 Fake-IP 时拒绝连接，加密连接仍校验原主机名的 TLS 证书。因此，若网关劫持 53 端口，引导 DNS 也需使用实际可达且返回真实 IP 的路径。

例如填写 `https://dns.example/dns-query` 时，测速服务器需要先知道 `dns.example` 的 IP，这一步使用引导 DNS；随后才连接该 DoH 服务查询节点服务器域名。设置界面会在需要时显示此字段，直接填写 IP 地址的 DNS 无需额外配置。已经填写的引导 DNS 仍会保留显示，方便修改或清空。

**OxiDNS 托管操作**：选择设备，核对配置空间，填写该设备可监听且 ConfigFlow 可达的 IPv4 地址和专用端口（默认 15353）。默认从该设备已发布配置中的上游列表选择，无需重新抄写 DNS 地址；只有一个支持复用的候选时自动选中，有多个时明确选择。也可切换“手动指定”填写其他 DNS，域名加密上游可指定一个引导 DNS。首次实现支持已成功发布原生配置、独占配置空间的单机 OxiDNS；未发布、非原生模式、共享配置空间或启用 HA 的设备会说明不可用原因。它不安装 OxiDNS，也不修改路由器劫持规则。专用上游自身若仍返回 Fake-IP，验证会失败并保留原测速设置。

现有上游候选只来自已确认的发布配置，不包括未发布草稿，也不把 OxiDNS 主监听入口当作上游。名称和地址只能说明配置内容，不能证明实际查询会返回真实 IP，因此候选统一视为尚未验证。复用保留受支持的上游参数；含不支持依赖或参数的候选会说明原因，不能悄悄省略这些参数。选择后若发布配置发生相关变化，需刷新重新选择。创建时复制所选的已发布参数，之后专用入口独立保存，不会随原上游的修改自动改变；需要更换上游时先切换测速模式、移除旧入口，再新建。

打开设置或选择上游时只读取配置，不发送 DNS 查询。点击“创建并启用”后，先发布专用入口，再从 ConfigFlow 经该入口查询 `example.com`；未返回有效地址、超时或返回识别出的 Fake-IP 时，不切换原测速设置。验证成功后才保存绑定。之后每次节点测速仍检查各节点服务器域名的实际解析结果。

托管发布从该设备最近确认的发布快照构造，只添加有归属标记的专用入口，保留已有规则文件，不夹带其他未发布草稿。成功后把这些入口合并回该设备所属配置空间，后续常规发布会保留它们。无需提取或同步节点域名列表，新增订阅节点会按测速所选 DNS 正常查询。

切换到系统或自定义 DNS 不会自动删除托管入口；需显式移除。入口仍被测速引用时不能删除；设备删除、迁移配置空间或切换配置模式也须先清理托管入口。端口冲突、手工修改入口或发布状态不明时会显示错误或等待确认，不会接管已有手工配置，不会自动换端口或退回系统 DNS。更新前已有的测速 DNS 地址按自定义模式保留。

“检测 DNS”从 ConfigFlow 实际运行环境通过同一测速组件查询固定域名 `example.com`，返回地址和耗时，不保存设置、不使用节点认证信息、不改测速历史。它验证当前解析路径，不保证所有节点域名都能解析。保存改变解析路径或引导 DNS 后，后续测速会开始新的历史。

三种模式都不改 NAS / 容器的系统 DNS、Mihomo、代理组或 Provider 健康检查配置；只有托管模式的显式创建/移除操作会发布 OxiDNS。不会改写保存的节点域名、TLS / Reality 的 SNI 或混淆插件的 Host。Fake-IP 检测覆盖常用的 `198.18.0.0/15`，自定义 Fake-IP 地址段仍需在 DNS 配置中排除节点服务器域名。

新后端会拒绝不支持 DNS 设置的旧版测速二进制，避免设置被静默忽略；需要一同更新后端与测速组件。

策略组配置页与规则命中模拟不使用这些历史结果推断目标设备的自动组选优。即使探测语义相同，两台机器的网络出口、DNS 和测试地址也可能不同；目标设备的实际延迟与选中节点以其 Mihomo 面板为准。

独立组件链接 Mihomo，按 GPLv3 分发，见 `backend/node-probe/LICENSE`；组件源码与锁定依赖在同目录。ConfigFlow 主应用继续沿用仓库根目录的许可证。
