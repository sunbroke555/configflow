# ConfigFlow 接入上游软路由（RouterOS / iKuai）

状态：P0 接入与差异报告、P1 分阶段发布及 DHCP DNS 下发、单条静态路由管理、ROS 远程规则增量同步、ROS 强制 DNS（DNS 劫持）已实现。本文以当前实现为准；未实现的能力列在第 9 节。

## 1. 目标与范围

旁路网关方案（mihomo fake-ip + OxiDNS）依赖主路由把代理网段送往 mihomo，并让这些流量不做源地址转换。部分网络还需要 mihomo 主机的回流规则，把经主路由转发的连接回包送回主路由；每台路由器可以单独开启“自动配置回流”，RouterOS 和 iKuai 都默认关闭。

ConfigFlow 根据当前配置空间、显式选择的规则集和 mihomo Agent 计算期望状态，读取设备配置生成差异报告，预览确认后执行一次整体发布。

当前管理范围是 **代理路由（RouterOS 静态路由或按规则集选择的来源策略路由，iKuai 端口分流）、NAT 免转换、选择 OxiDNS 后的 DHCP DNS 下发，以及显式开启后管理的 mihomo 主机回流规则**。不管理 WAN、无线、PPPoE 或防火墙全量配置。与期望状态一致的手工对象可以在预览后接管；自动发布保留无关的手工路由；“管理路由”可在明确预览确认后单独修改用户选中的普通静态路由。

## 2. 接入方式

| 项目 | RouterOS | iKuai |
|---|---|---|
| 支持版本 | 7.1+ | 仅 4.x，3.x 拒绝接入 |
| 连接方式 | REST `/rest/...`，HTTP/HTTPS + Basic 认证 | Web 管理接口 `/Action/login`、`/Action/call` |
| 账号要求 | HTTPS 启用 `www-ssl`，HTTP（7.9+）启用 `www`；用户具有 `api`、`rest-api`、`read`、`write` 权限 | 管理员账号 |
| 读取 | 版本、静态路由、NAT 免转换、地址列表、DHCP 网段与 DNS | 版本、静态路由、端口分流、当前路由表、NAT 免转换及关联地址对象、DHCP 网段与 DNS |
| 写入 | REST 自动增删改，阶段完成后回读校验 | Web 管理接口自动增删改，阶段完成后回读校验 |
| 失败处理 | 逆序执行本次操作的撤销动作，记录回滚结果 | 同左 |

两种路由器都由 ConfigFlow 服务端直连，不在路由器上安装 Agent。RouterOS 发布不再要求用户复制或导入 `.rsc` 脚本；当前没有 API-SSL 回退通道，也没有脚本导出入口。连接探测成功只证明对应读取请求可用，不等于已经验证写权限或完整流量路径。

## 3. 数据模型与期望状态

路由器记录保存在当前配置空间的 `routers.items` 下，可编辑字段为：

```yaml
routers:
  items:
    - id: router_xxx
      name: 主路由
      type: routeros              # 或 ikuai
      endpoint: https://192.168.1.1
      username: configflow
      password: ...
      verify_tls: true
      proxy_gateway_agent_id: ... # mihomo Agent
      manage_return_routing: false # 自动配置回流，默认关闭
      dns_agent_id: ...           # 所选 OxiDNS Agent；为空时不管理 DHCP DNS
      ip_rule_sets: [...]         # ROS 静态路由规则集 ID；iKuai 保持原用途
      ros_policy_rule_sets: []    # ROS 专用，独立选择策略路由规则集；默认空，与上方互斥
      auto_rule_sync: false      # ROS 远程规则更新后自动同步，默认关闭
      rule_sync_interval: 60     # 分钟，可选 15/30/60/180/360/720/1440
      dns_guard:                 # ROS 专用，强制局域网 DNS 走 OxiDNS；缺省等同全部关闭
        enabled: false
        block_dot: false         # 拦截 853（DoT / DoQ）
        failover: true           # Netwatch 在 OxiDNS 无应答时暂停劫持
        bypass: []               # 额外放行的 IPv4 地址或网段
      dns_guard_state: ...       # 只读，最近一次发布写入的对象 ID 与回读配置
```

编辑时密码留空保持不变。前端接口返回 `has_password`，不返回密码；脱敏导出移除密码，并隐藏用户名与管理地址。当前尚未实现独立的 `secret_ref` 凭据模型。

`manage_return_routing` 是每台路由器的独立布尔设置。新建默认为 `false`，旧记录缺少该字段时也按 `false` 处理，读取接口补齐默认值；前端保存时显式提交布尔值。关闭只停止 ConfigFlow 对回流规则的管理，不删除或停用之前已有的规则。

| 期望对象 | 当前来源 |
|---|---|
| 代理网段 | mihomo `fake-ip-range` 始终包含；再加入用户显式勾选规则集中的 IPv4 CIDR，并合并网段 |
| 代理下一跳 | 所关联 mihomo Agent 的 host |
| 新增 NAT 免转换的源范围 | mihomo host 所在 `/24` 的可用地址，排除 mihomo 自己；当前不是自动发现全部 LAN 网段 |
| NAT 免转换的目的范围 | 需要代理且被判为可能受源 NAT 影响的网段，排除本次路由冲突而跳过的项；RouterOS 对无需免转换的网段不新增规则 |
| DHCP DNS（关联 OxiDNS 时） | 所选 OxiDNS Agent 的 IPv4 host，替换包含所选 mihomo 网关的唯一 DHCP 网段的 DNS 列表 |
| 回流标记的目的范围（开启时） | 期望代理网段与发布后已有 NAT 免转换目的网段的并集 |
| 回流下一跳（开启时） | 路由器管理地址中的 IPv4 地址 |

始终需要关联 mihomo Agent 配置，以获取代理路由下一跳和 DHCP 目标网段。自动配置回流关闭时，不读取 mihomo Agent 回流状态，不要求该 Agent 在线，也不要求路由器管理地址本身是 IPv4；路由器接口仍须可连接。开启后，路由器管理地址不是 IPv4、mihomo Agent 离线或无法读取回流状态会阻止发布。关联 OxiDNS 后，DHCP DNS 下发另要求所选 OxiDNS Agent 有效、在线且 host 为 IPv4。仅选择 `dns_agent_id` 不会触发 DNS 劫持或 DHCP 静态绑定写入；DNS 劫持需在 RouterOS 上另行开启（见 4.6）。

## 4. 路由器写入

### 4.1 代理路由

**RouterOS** 提供“使用静态路由的 IP 规则集”和“使用策略路由的 IP 规则集”两组独立选择，均可直接从可用规则集中选择。选到另一组时自动移出原组；API 拒绝同一规则集同时出现在两组。两组均未选择的真实 IP 规则集不下发，fake-ip 始终使用静态路由，不按网段数量自动切换。旧配置中上方总范围与下方策略子集的重叠，读取时按原先实际方式拆分（策略优先）；只读不会改写配置，后续保存使用独立列表。

- 缺失的期望网段：新增静态路由，下一跳指向 mihomo。
- 已存在且有效、下一跳正确的主表手工路由：修改备注为 ConfigFlow 标记，接管原对象，不删除重建。
- 不再需要的受管主表路由：删除；其他路由表不参与静态组同步、接管或清理。
- 同网段的下一跳不符或其他冲突：提示并跳过该网段，不直接覆盖。跳过也保留该网段原有的 Agent 回流覆盖；不会因整集合替换而删除保护，也不会为原先未保护的部分新增回流。无关手工路由保持不变。
- 报告、接管、发布校验和静态 NAT 出口判断共用有效路由选择：读取运行状态和距离后，按最长前缀检查整个目的范围；即使没有同网段路由，更具体的错误下一跳也在预览时报告冲突。已禁用的备用路由不作为出口竞争者。错误聚合路由若被正确、有效的更具体路由完全覆盖，不再误报冲突；此时只接管并保留证明完整覆盖所必需的正确路由，不接管错误聚合路由。 每次设备读取后在本批检查中复用网段索引和下一跳出口结果，按地址范围检索相关子网；不逐目的重新解析整张表。索引在本批结束后释放，不跨请求或设备写入复用，也不进入预览指纹。

ROS 来源策略使用当前配置空间**已保存的 OxiDNS 设备策略**。仅显式设为 `smart` 的 IPv4 地址或网段进入来源列表，按最长前缀处理 `direct` / `smart` 例外，再排除 Mihomo host；未列出的设备不会自动加入。该来源与 DHCP DNS Agent 选择独立，用户需同步发布 OxiDNS 设备策略。自定义 OxiDNS 路径不能确认、没有智能分流来源或选中规则集无法完整读取时阻止发布。

发布创建专用来源、真实 IP 目的和网关排除地址列表、带 FIB 的独立路由表，以及指向 `mihomo@main` 的默认路由；确认下一跳生效后，最后添加 `prerouting` 入口，通过来源和目的列表匹配并进入专用链设置 `mark-routing`。路由器本机地址不匹配入口，Mihomo 自身也排除在来源之外。这些是 ROS 路由标记，与 Linux 回流功能的 `fwmark` 无关。需要 NAT 免转换时，单独创建同时限定来源列表、目的列表和 LAN 出口的 `srcnat accept`，不扩充共享列表。

策略资源按用途命名，同组共用编号：`CF_Source_Proxy_IP_01`、`CF_Destination_Proxy_IP_01`、`CF_Bypass_IP_01`，路由表和专用 Mangle 链均为 `CF_Proxy_Routing_01`。名称只使用字母、数字和下划线，编号不表示优先级。依次检查 `01` 至 `256`，任一名称已存在或被引用（包括空列表引用、否定匹配和下一跳的 `@表名`）时避让整组；没有空闲组则阻止发布。更新先用另一空闲组创建并激活，再按归属记录清理旧组，失败按原记录回滚；无变更时保留当前编号。旧 `cfp_…` 名称通过命名版本变化在下一次预览、发布时迁移，不直接重命名正在使用的对象，也不凭 `CF_` 前缀接管或删除对象。

差异报告把来源策略单独列出，并允许查看实际来源范围，不要求这些目的另有静态路由。静态组与策略组的 CIDR 可以重叠：命中策略时查独立路由表，未命中时继续使用主表已有静态或默认路由。无关手工路由保持不变。完整可恢复、指向同一 Mihomo 的受管主表路由若仍覆盖已转为纯策略的目的，会在新策略激活后迁移，包括旧的聚合路由；删除前先确认仍选中的静态部分已有有效替代路由，不能因聚合范围重叠而保留过期覆盖。迁移按具体对象 ID 排除普通清理，避免重复删除。已启用的 FastTrack、不能确定优先级的既有 Mangle 分流、路由规则或非 main VRF 仍会阻止发布。

静态转策略时，同时从旧受管 NAT 免转换中减去仅属于策略的目的范围，保留其余目的、来源及其他匹配条件和规则位置；纯策略免转换仅通过来源、目的和 LAN 出口三重限定。保留的 NAT 目的范围同步纳入 Agent 回流目的集合，即使它们不在本次选中的路由规则集中，也不丢失原有回流保护。无法安全拆分时阻止发布；尤其列表型目的条件不会被静默改写成固定地址规则，须先人工核对。迁移失败时，旧路由、NAT 匹配范围和顺序一并补偿。

策略转静态或迁移聚合路由需要建立替代静态路径时，先准备回流，再在同一受保护、可补偿的策略事务内准备静态 NAT、建立并回读替代路由，最后才撤销旧策略及其 NAT。提前准备的新增 NAT 免转换限定已确认的 LAN 出口，避免路由尚未切换时误免除 WAN 流量的源 NAT。准备操作复用驱动的写后回读与逆序补偿；回滚先恢复旧路径，再撤销新保护。旧路径恢复失败时保留新保护并报告回滚不完整，不继续移除保护。

撤回前还必须逐一证明旧策略的“来源 × 转入静态的目的”在实际 LAN 出口不会发生源 NAT，不能只依赖目的网段的 `synced` 状态。校验按 NAT 规则顺序排除即将删除的旧策略保护，仅用来源、目的和出口可确认的无额外限制 `accept` 规则消除待保护范围；窄来源、仅 TCP 等额外条件、错误出口及位于转换规则之后的免转换均不能证明完整覆盖。无法证明时停止撤回并补偿已准备的操作，保留旧策略及归属；不默认为所有来源补一条宽泛免转换规则。

读取 `/routing/settings` 的 `policy-rules`，确认 Mangle 查找早于主表和用户路由规则；未知或相反的查找顺序阻止发布，并纳入预览指纹和回读。策略的 NAT 出口根据其独立表中指向 `mihomo@main` 的下一跳判断，主表只用于解析 Mihomo 网关的有效直连出口，不用主表目的路由推断策略流量出口。写入独立表路由后，在启用 Mangle 前确认其 active 状态及 immediate-gw 与预览一致；发布后重复核对。普通静态路由的 NAT 判断仍沿用主表目的查找。

资源名称自动避开已有名称，私有 `ros_policy_state` 记录本次创建对象的 ID 和完整配置，后续只管理核对一致的对象。名字或 `cf` 前缀不能单独证明归属；外部修改、重排或其他 Mangle、NAT、Filter、Raw、路由规则引用这些对象时保留现场。每步写入后回读，失败按逆序补偿；恢复删除对象时同步记录新的 ID。REST 不提供跨对象原子事务；进程中断、归属不明或回滚失败须检查现场，不自动清除不明对象。

清空策略选择并发布，会撤销本功能的策略资源，不自动为取消的规则集新增静态路由。需要切换为静态时，显式在静态组选择；替代静态路由冲突时阻止发布，写入后未生效时保留旧策略并回滚本次变更，不能跳过替代路由后直接撤回有效策略。只保存设置不修改路由器。仍有受管策略时，需先发布撤销再修改路由器类型或管理地址；删除接入记录也返回 409，须先清空策略选择并成功发布撤回，避免丢失仍在生效的对象归属。

**iKuai** 使用端口分流（`stream_ipport`，分流方式“下一跳网关”），不再使用静态路由。

静态路由只看目的地址：mihomo 自己直连代理网段时（例如 iKuai 线路检测 ping 8.8.8.8 后由 mihomo 转发），包被同一条路由送回 mihomo，经 iKuai 改写源地址后再次转发，形成持续回环。实测高峰每秒 7000 多个包，mihomo 与主路由 CPU 明显升高。端口分流可以按源地址排除网关，从根本上避免回环：

| 规则 | 目的地址 | 维护方式 |
|---|---|---|
| `cf-mihomo` | 期望代理网段（fake-ip 与所选规则集） | 完全受管：与期望状态同步增删 |
| `cf-mihomo-manual` | 从指向 mihomo 的手工静态路由迁移来的网段（如公共 DNS 地址） | 只增不删，可在 iKuai 手工调整 |

两条规则相同的部分：源地址“除 mihomo 外”（反向匹配），协议任意，下一跳 mihomo，优先级 0（最高，避免多线负载、协议分流等规则先把代理流量送往 WAN）。

- 发布先写入或更新规则，再删除所有指向 mihomo 的启用静态路由（含手工路由）。静态路由优先于端口分流，删除前流量仍按原路由到达 mihomo，过程不断网。
- 被期望网段覆盖的子网路由直接删除，不单独迁移；已停用的静态路由不承载流量，保持不变。
- 回读校验规则的源排除、下一跳、协议、优先级与目的网段；不一致时按相反顺序恢复静态路由并删除新规则。

**内核残留路由**：iKuai 修改或删除静态路由后，内核中可能残留旧路由（实测为修改优先级后留下的 `prio 20` 路由）。它不出现在静态路由配置中，界面和接口都无法删除，却优先于端口分流，会让回环继续。ConfigFlow 读取“当前路由表”（`static_rt_table`），把配置无法解释、指向 mihomo 的路由列为预览警告；路由阶段校验通过后再查一次，有残留时在发布日志中记录“需处理”，不回滚（回滚也无法清除）。处理方法是重启 iKuai，内核会按配置重建路由表。

### 4.2 NAT 免转换

RouterOS 使用 `/ip/firewall/nat` 的 `chain=srcnat action=accept`；新增规则放在源 NAT 转换规则之前。iKuai 使用 `nat_rule` 的过滤动作。

**没有显式免转换规则，不等于需要补规则。** RouterOS 会结合代理下一跳的出口和当前源 NAT 规则判断：例如 mihomo 经 `lan4` 到达，而现有 masquerade 仅匹配 `pppoe-out1` 或不含 `lan4` 的 `WAN` 接口列表时，旁路流量本身不会被这些规则转换。

| NAT 报告状态 | 含义与发布行为 |
|---|---|
| `synced` / `adoptable` | 已有显式免转换规则覆盖，分别为已受管或可接管；保留原有处理方式 |
| `not_required`（无需免转换） | 没有潜在源 NAT 转换规则，或现有转换规则均可按出口排除；计入同步状态，不生成 NAT 写入操作 |
| `missing`（缺失） | 普通源 NAT 转换规则可能匹配且没有相应免转换规则，按计划新增或扩充 |
| `unknown`（待确认） | 出口或源 NAT 匹配证据不足；报告说明原因，不自动新增，并通过计划阻塞项禁止误下发 |

这是保守的配置判定，不是完整防火墙模拟，重点判断转换动作与出口条件。普通源 NAT 规则无法按出口排除时，即使带有源地址、端口或协议限制，也按“可能匹配”处理，不断言所有客户端都会被转换。复杂接口列表、策略路由或 VRF、出口不明确，以及无法排除的未知 NAT 动作会保留“待确认”；不假定 mangle、递归下一跳或自定义规则链都能完整推演。没有任何潜在源 NAT 转换规则时，也无需新增免转换规则。无需免转换不影响代理路由，回流是否管理由独立开关决定。

已覆盖目的网段的手工免转换规则可以接管。需要增加目的网段时，优先扩充已受管或本次接管的规则；没有可扩充的规则时才新增。

**RouterOS 扩充规则时保留原有限制**：读取原规则的实际可写配置，为新增目的 CIDR 创建规则，仅替换目的地址、移除旧的 `dst-address-list` 引用，并使用受管备注。原有 `src-address`、`src-address-list`（包括否定条件）、接口、协议、端口及其他匹配限制保留；不修改可能被其他规则引用的共享地址列表。接管原规则只修改备注。新建规则的源 IP 范围转成 CIDR 后直接写入规则，不创建共享 `cf-nat-src` 地址列表。

同一规则组拆成多个源 CIDR 时，后续扩充会为所有源分片分别生成预览操作；除源地址外的条件必须一致，不混合不同源地址列表、接口或协议限制。原始匹配条件也参与计划指纹，执行前再次核对，避免源范围在预览后被改变。

对于需要显式免转换的网段，NAT 差异报告与发布回读仍主要检查启用的受管规则是否覆盖目的网段，尚未完整推导源地址、接口、协议、规则顺序等条件下的实际流量覆盖。因此“无需免转换”或回读通过都不代表所有客户端的实际转发路径已完成流量验收。

### 4.3 设备对象与撤销

RouterOS 写入前读取相关对象的可写配置，成功后返回相应撤销操作；新增项撤销时删除，修改项恢复原值，删除项按保存的配置恢复。本次操作产生多个对象时也需记录并撤销相应变更。

复合 NAT 操作中途失败时先补偿本次已写入项，再撤销之前的发布操作。对响应超时或损坏的新增请求，通过提交前后对象 ID 与字段核对定位新增项；无法唯一确认或撤销失败时，明确记录“回滚未完成”，不把状态未知当成成功。REST 的方法与规则位置参数遵循 [RouterOS 官方 REST 文档](https://manual.mikrotik.com/docs/developer-guides/rest-api/)。

iKuai 的 add/edit/del 参数与字符串编码按 Web UI 约定处理；edit 前读回完整记录，撤销使用读回的原记录。名称 `tagname` 必填且为 1–15 字符，新增对象使用 `cf_rt_<hash>` / `cf_nat_<hash>`；备注使用 `cf-<原备注>`，归属识别兼容 `cf:` / `cf-`。

### 4.4 DHCP DNS 下发

“DHCP DNS 服务器（OxiDNS Agent）”选择本身就是管理开关，不增加其他布尔设置。默认未关联时保留路由器现有 DHCP DNS；选择后，以该 Agent 的 IPv4 host 为期望 DNS。

只定位**包含所选 mihomo 网关的唯一 DHCP 网段**。成功定位后，把该网段的原 DNS 列表替换为仅包含所选 OxiDNS 地址的列表，**不保留旧备用 DNS**。不修改 DHCP 网关、地址池、租期、静态绑定或其他网段；也不自动创建 DHCP 服务。预览明确列出网段及“旧 DNS → 新 DNS”，用户确认后才写入。

DHCP DNS 报告包含 `status`、`message`、`target_dns`、`items` 和 `blockers`。每个 item 展示网段、当前 DNS 列表、期望 DNS 列表、状态及说明：

| 状态 | 展示与处理 |
|---|---|
| `disabled` | 未关联 OxiDNS，不管理 DHCP DNS，保留现有值 |
| `synced` | 唯一目标网段的 DNS 已是所选服务器，无需写入 |
| `pending` | 唯一目标网段需要更新 DNS，列入发布预览 |
| `unknown` | 目标或配置证据不足，列出原因并阻止发布；多匹配时展示候选网段 |

所选 OxiDNS 无效、离线或不是 IPv4，没有匹配 DHCP 网段、匹配多个网段，或自定义 DHCP option 可能覆盖 DNS 时，不猜测或批量修改。当前 DNS 列表为空时显示“自动/未指定”；这不代表终端没有 DNS，例如 RouterOS 可能继承主路由 DNS。

RouterOS 通过 `/ip/dhcp-server/network` 只修改 `dns-server` 和 `dns-none`，并检查 network、server、lease、option set、matcher 以及 RADIUS 的潜在 DNS 覆盖；相关证据无法读取时阻止发布。选项优先级及字段依据 [RouterOS DHCP 文档](https://help.mikrotik.com/docs/spaces/ROS/pages/24805500/DHCP) 和 [DHCP network 命令参考](https://manual.mikrotik.com/docs/cli-reference/ip/dhcp-server/network/)。

iKuai 的字段取自官方 4.0.120-beta Build202603191336 固件内的 DHCP 前端、后端及数据库表结构。`dhcp_server edit` 需要完整表单，因此保存并回读校验全部字段，仅把 `dns1`、`dns2` 都设为所选服务器；两处使用相同地址，避免备用 DNS 留空时产生继承歧义，报告中去重显示。`dhcp_static` 里同网段的独立 DNS 覆盖会阻止发布。遇到未验证的新字段、缺失字段或不完整列表时停止，避免覆盖未知配置。

存在代理路由冲突时阻止 DHCP DNS 下发。写入前再次确认唯一目标网段、路由和 NAT 状态；即使 DNS 已同步而本次只修改路由，末阶段仍回读 DNS。预览指纹包含 DNS Agent、目标地址、网段及覆盖选项的语义配置；普通租约倒计时不影响指纹。

DHCP DNS 阶段在路由下发后执行，写入后回读，失败时按原值撤销。它更新 DHCP 服务端配置，不强制断开客户端或修改客户端已获取的租约。**终端在 DHCP 续租或重新联网后获得新 DNS**；这一步本身不做 DNS 劫持。可选的强制 DNS 阶段随后独立执行，见下文 4.6；两者都不能代替实际 DNS 查询验收。

### 4.5 单条静态路由管理

RouterOS 行同时提供“策略路由”入口：`GET /api/routers/<id>/policy` 只读取本配置空间发布记录中按资源 ID 对应的地址列表、Mangle、路由表、下一跳及 NAT 免转换对象。显示实际字段、外部修改与缺失状态，不按名称接管手工对象；大列表可搜索、分页。入口内以“来源设备 / 规则集与网关 / 发布预览 / 已下发对象”组织操作。来源设备是当前配置空间共用的 OxiDNS 策略，与这台 ROS 的规则集和网关通过 `PUT /api/routers/<id>/policy-settings` 一起校验、原子保存；草稿修订冲突时拒绝覆盖。保存后只生成预览，不写设备。来源设备页直接提供已有客户端选择，只在打开客户端下拉框时读取查询样本。预览展示选中的同空间 OxiDNS 目标和紧凑的 ROS 阶段变更清单，明确提示 DNS 发布完整已保存配置，并固定完整配置修订号；不在面板展示整份 YAML。每项路由操作可展开查看具体字段：来源与目的范围的增删保留、网关、Mangle、路由表、NAT 和实际清理列表。详情只读取预览操作数据，不展示无关设备配置；大列表按需展开、支持搜索和分页。明确确认发布后，逐台沿用 Agent 事务发布并确认成功，最后按预览指纹发布 ROS；失败或结果待确认就停止后续步骤，保留已成功设备的结果，不宣称跨设备原子回滚。也可明确取消全部 DNS 目标，仅发布 ROS。未保存修改离开时提醒，发布期间禁止切换上下文；未知发布结果按原部署 ID 查询，不自动重新提交。

路由器编辑表单保留“保存设置与确认发布”的必要提示，账号权限、管理接口、回流、规则集及 DHCP DNS 的详细说明放在对应选项旁的问号中；鼠标悬停、键盘聚焦或点击均可查看。保存并预览期间离开页面或切换配置空间后，旧请求不会继续生成预览。

路由器列表的“管理路由”入口直接读取设备路由，无需生成差异报告或等待 mihomo Agent 在线。支持添加、编辑和删除普通 IPv4 静态路由，可修改目的网段、IPv4 下一跳、启用状态和备注。RouterOS 仅编辑主表中的普通静态路由；动态、直连、非主表、特殊下一跳或含无法安全保留字段的对象只读，并显示原因。iKuai 完整分页读取 `static_rt`，保留接口、优先级、名称等原表单字段。

- `GET /api/routers/<id>/routes` 返回路由列表和原始配置版本摘要，不返回内部快照。
- `POST /api/routers/<id>/routes/plan` 接收 `action`（add/update/delete）、原记录 `id`/`revision` 及四项 `values`，只生成完整前后对比及指纹。
- `POST /api/routers/<id>/routes/apply` 携带相同参数与指纹，重新读取设备并确认预览仍有效后才写入。预览过期返回 409，界面保留草稿并要求刷新后重新确认。

每次只修改用户选中的路由，不运行 NAT、DHCP DNS 或 mihomo 回流阶段。新增路由不自动添加 `cf` 管理前缀；用户保留或填写该前缀时，界面提醒后续自动发布仍可能调整或删除该受管路由。禁止重复添加主表同目的网段；编辑保留未开放字段，删除失败时尽可能完整恢复原配置。

应用内的手工路由写入和自动发布按路由器连接串行执行。写入前还会比较稳定配置快照，写入后回读；失败时仅在最新快照仍可确认属于本次变更时补偿。设备 API 没有条件写入机制，无法彻底消除外部程序在检查后瞬间修改的竞争；身份或最终状态不明时保留现场并报告补偿未完成，不猜测删除或覆盖外部变更。

### 4.6 强制 DNS（RouterOS）

写死公共 DNS 的设备会绕过 DHCP 下发的 OxiDNS。开启「强制局域网 DNS 走 OxiDNS」后，RouterOS 把局域网发往其他地址的 53 端口查询转给 DHCP DNS 所选的 OxiDNS。实现位于 `backend/routers/dns_guard.py`，仅 IPv4，仅 RouterOS。

**前提**：必须已选择 DHCP DNS 的 OxiDNS Agent，并沿用其校验（在线、IPv4 host）；OxiDNS 必须位于路由器唯一的活动直连网段内，入口接口与局域网网段由该直连路由推导；OxiDNS 地址不能落在代理目的网段内。缺任一条件、存在代理路由冲突，或保留名称（地址列表 `cf-dnsguard-bypass`、Netwatch `cf-dnsguard`）已被其他对象占用时阻止发布。

**写入对象**（按顺序创建）：

| 对象 | 内容 |
|---|---|
| 放行地址列表 `cf-dnsguard-bypass` | OxiDNS、mihomo 网关及用户填写的放行项 |
| srcnat 回包（UDP / TCP） | 源为局域网网段、目的为 OxiDNS:53、出口为同一接口的 masquerade，追加在 NAT 末尾 |
| dstnat 劫持（UDP / TCP） | 入口接口上、来源不在放行列表、目的不是 OxiDNS 且不是路由器本机的 53 端口查询 dst-nat 到 OxiDNS:53，放在 NAT 列表最前 |
| filter 853（可选） | TCP reject（tcp-reset）、UDP drop，放在 filter 列表最前 |
| Netwatch（默认开启） | 每 10 秒检测 OxiDNS 的 TCP 53（超时 2 秒，开机后 30 秒开始检测）。持续 15 秒无应答才停用、恢复时立即启用备注为 `cf-dnsguard:hijack` 的规则；切换时清除仍走旧路径的 53 端口连接；不修改路由器自身 DNS |

回包规则不依赖 `connection-nat-state`（部分 7.x 的 NAT 不支持）。因正常客户端在同一网段直达 OxiDNS、不经过路由器，该规则只会匹配被劫持的查询。

**归属**：对象只通过 `dns_guard_state` 中的设备 ID 与写入后回读的配置识别；`cf-dnsguard:` 备注仅供人工辨认。受管对象被外部修改时保留现场并阻止发布；Netwatch 切换劫持规则的停用状态不算修改。设置变化时先删除旧受管对象，再按顺序创建新对象；删除或创建失败时逆序恢复，被恢复的对象获得新 ID 后清单随之更新。关闭开关后只删除清单中核实过的对象，手工规则保留。

**NAT 判断**：已核实归属的回包规则只转换发往 OxiDNS:53 的查询，判断代理路径是否需要 NAT 免转换时不计入，避免为它额外生成免转换规则；未能核实归属时仍按普通源 NAT 规则保守判断。

**报告**：`dns_guard` 段给出状态（未开启 / 已同步 / 待更新 / 待确认）、每个对象的作用与状态，以及被 Netwatch 暂停的劫持规则；路由器上其他 53 端口 dst-nat / redirect 规则以警告列出，不自动删除。

**故障切换细节**：RouterOS 的连接跟踪会让同一源端口的后续查询沿用首次的 NAT 决定（UDP 流最长约 3 分钟）。暂停时删除被转给 OxiDNS 的 53 端口连接，恢复时删除暂停期间直连其他 DNS 的连接（放行列表中的地址，以及 /30 及更小网段展开后的地址除外），使固定源端口的客户端立即改走新路径；删除约 1 秒后生效，恰在途中的查询可能需要客户端重试一次。Netwatch 自带的 `startup-delay` 默认 5 分钟，这里改为 30 秒，缩短路由器与 OxiDNS 同时重启时的无 DNS 时间。

已知限制：Netwatch 只检测 TCP 53 能否连接，OxiDNS 仍在运行但解析异常（如上游失效）时不会暂停劫持。RouterOS 先处理 mangle 再做 dstnat，若写死的 DNS 地址恰在来源策略路由的目的网段内，这类查询会按策略送往 mihomo 并由其应答。

## 5. mihomo Agent 回流规则

回流规则应用在 **mihomo 主机**，由 Go Agent 管理，不写到 iKuai 或 RouterOS 上。“自动配置回流”适用于需要将回复经主路由返回的网络，默认关闭。

关闭时，报告返回 `return_routing.status = disabled`，界面以中性状态说明已关闭，不显示缺失、异常或“未发现”。生成报告、预览和发布都不调用 Agent 回流读取、写入或删除接口；已有规则及 Agent 保存的回流状态保留，关闭不会撤销之前发布的配置。

开启时才执行以下管理逻辑，并保留校验与失败回滚流程：

- 使用独立 nftables 表 `inet configflow_return` 和匿名集合，通过归属记录及具体规则句柄更新自己的对象，不改 mihomo 自己的表。
- 首次分配优先使用 mark `0x400000`、路由表 `104`、`ip rule priority 104`；默认值被占用时只选择可证明空闲的其他值，并通过 `safety.allocation` 返回分配结果。不修改全局 `send_redirects` 设置，该设置不属于本功能独占管理的资源。
- 校验 mark 与 mihomo `routing-mark` / auto-redirect 标记不重叠、路由表与 `iproute2-table-index` 不冲突、优先级小于 `iproute2-rule-index`；检查 `nft`、`ip` 等依赖。还须读取系统实际使用的 nftables 标记、策略路由和路由表，确认目标资源未被其他配置占用。
- 根据 mihomo 运行模式处理回包；TUN 模式需要处理从 TUN 网卡进入的 UDP 回包。
- 通过主路由源 MAC 限定需要打标记的连接。客户端直接把 Agent 当网关，或绕过主路由直连 Agent 的连接，不强制回送主路由。
- 没有既有管理状态时，可以避开其他程序占用的标记、路由表或优先级；不接管或删除手工表，也不禁用其启动脚本。已有无归属状态、未完成事务或受管资源发生外部变更时仍阻止操作，不通过重新分配绕过冲突。`adopt_legacy` 不再用于发布。
- 期望状态和归属证据保存在 Agent 目录的 `return-routing.json`。只有可以核实归属的 ConfigFlow 对象才允许更新和撤销；旧状态没有归属证据而相关资源已经存在时阻止操作。Agent 启动时重新应用也必须通过同样的安全检查。

开启后的接口为 `GET /api/return-routing` 查询、`PUT /api/return-routing` 应用。GET 必须返回 `safety = {version: 1, ok: true, blockers: []}` 才能发布；缺少该能力的旧 Agent、结果格式不完整或检查有阻塞项时，预览和执行都会停止。PUT 的配置必须携带 `safety_version: 1`，Agent 在写入前重新检查占用；不能仅凭预览时的结果放行。

`safety.allocation` 包含 `version`、`table`、`priority`、`mark` 和 `reused`，只表示本次读取后选出的值，不占用或写入资源：

- 路由表依次尝试 `104`、`105..252`、`1..103`，跳过系统路由、策略规则、VRF 和 mihomo 已使用的表。
- 策略优先级同样先尝试 `104`，再向更大的值查找，最后尝试 `1..103`；候选必须在 `1..32765` 内且严格小于 mihomo 的策略入口优先级。
- mark 只选单个 bit：先尝试 bit 22（`0x400000`），再按 bit 23..31、bit 0..21 的顺序查找，避开 mihomo、系统策略规则掩码和 nft 规则使用的位；无法证明空闲时阻止发布。

成功发布后把分配结果和归属清单持久化，后续发布及启动重放复用这些值（`reused: true`），不因更早的默认值重新空闲而迁移。已有自有资源缺失时可在重新检查后修复；无有效归属记录、`pending` 事务或外部改动仍会阻断，不能靠换表、换优先级或换 mark 遗留旧资源。

发布失败需要撤销本次新建的回流配置时，调用 `DELETE /api/return-routing`（不请求 legacy 恢复），仅清理由本次管理记录确认归属的对象：按具体句柄删除自有 nft 规则后删除空链，按具体选择条件删除自有策略规则和路由，不按优先级批量删规则、不清空整个路由表。带归属注释的空 nft 表和管理记录会保留，状态变为 `active: false`，`managed.table_present` 返回 `false`，下次启用时重新建立规则。撤销前仍确认 Agent 支持新版安全能力；占用变化不会授权删除第三方对象。已有受管配置的更新失败时尝试恢复此前的配置。关闭开关本身不会调用删除接口。

## 6. 发布流程

### 6.1 预览与确认

`POST /api/routers/<id>/plan` 只生成操作计划、阻塞项、警告和计划指纹，不写设备。

用户确认后，`POST /api/routers/<id>/apply` 携带预览的 fingerprint。服务端重新计算计划；指纹变化返回 409，并把新计划返回给界面。指纹一致且没有阻塞项，才执行写入。当前入口是手动预览与确认，没有定时自动发布。

发布、单路由操作及受锁保护的接入设置操作，在取得连接锁后清除请求内配置缓存，再读取持久化配置。若等待期间接入记录变化或删除，返回 409；发布必须在这次核对后才建立驱动连接，不能用锁外读取的旧地址或凭据执行旧计划。发布、接入编辑与删除、策略设置保存、自动同步设置保存和会持久化状态的连接探测共用跨进程设备连接锁；首次策略发布尚未保存归属时，也不能被另一进程删除或改写接入记录。纯设置读取不占用写入锁。

上述归属约束在配置仓储提交边界统一执行，配置空间导入、整库导入、重置、配置空间删除和普通配置保存均不能绕过。活动 `ros_policy_state` 存在时，禁止删除或替换归属及修改设备类型、地址；HTTP 冲突返回 409。同一类型和地址下允许更新用户名、密码及 TLS 校验设置，保留原归属记录，以便设备侧修改密码或证书后恢复接入；连接修复本身不写设备，后续发布仍逐项核对原归属对象。凭据和 TLS 设置更新同样受设备锁保护，不能与发布或同步并发。尚无归属记录的首次发布期间，涉及删除记录或替换连接的仓储提交也必须取得同一设备锁，锁被占用时立即拒绝，不在持有文档锁时等待发布。只有持有发布锁的专用回读保存路径可更新或清除归属，且保留期间发生的无关元数据编辑。

RouterOS 指纹还包含 NAT 判定依据（路由出口、NAT 条件、策略路由及所用接口列表），即使生成的写入操作相同，依据变化也需要重新预览；流量计数器不参与指纹。开启回流时，安全检查结果及 `safety_version` 也参与指纹。

### 6.2 分阶段顺序

1. mihomo Agent 回流规则，仅在开启自动配置回流时执行。
2. 主路由代理静态路由。
3. 主路由 NAT 免转换。
4. DHCP DNS，仅在关联 OxiDNS Agent 时管理。
5. 强制 DNS（RouterOS），仅在开启或仍有已发布对象需要撤销时出现。

两种路由器的计划都保留前四个阶段；强制 DNS 阶段只在用到时加入，未使用的路由器计划与报告保持不变。回流默认跳过，未关联 OxiDNS 时 DHCP DNS 也跳过；被关闭的阶段带 `enabled: false`、空操作列表和说明 `note`，明确本次不管理且保留原有配置。即使整个计划没有变更，预览仍展示该说明。按上述顺序自动执行已启用且有变更的阶段。

需撤销旧来源策略或迁移旧聚合路由时，第二阶段内部先准备 LAN 出口限定的静态 NAT，再建立并验证替代静态路径，最后撤销旧资源；这些 NAT 写入与路由操作共用该事务的回滚日志，不等到第三阶段才补保护。阶段完成后仍按统一检查回读最终路由与 NAT 状态。

RouterOS 存在“无需免转换”网段时，即使 NAT 阶段没有写入，也会重新读取出口与源 NAT 条件，确认判断仍成立。开启回流后，即使该阶段没有变更，也会在执行后续路由器操作前重新校验受管配置和安全检查结果。每个有变更的阶段完成后回读校验，通过才继续。失败时停止后续阶段，并尝试按相反顺序撤销已完成操作；回流开启时，NAT 免转换先于回流规则撤销。回流关闭时，不进行回流校验或回滚，也不因缺少回流状态而阻止路由器配置发布。

DHCP DNS 在路由器阶段中靠后应用，若其写入或回读失败，先撤销本次 DNS 变更，再按相反顺序撤销此前已完成的阶段。强制 DNS 写入前同样重新确认代理路由与 NAT，被劫持的设备会立即拿到 fake-ip。

### 6.3 当前回读校验

- 回流阶段（开启时）：Agent 的新版安全检查通过；受管 nftables 表存在；代理目的网段、下一跳、标记、路由表、优先级和安全握手与计划相符；策略路由的优先级、表号、标记及掩码与计划一致。关闭时跳过，不读取 Agent。
- 路由阶段：RouterOS 期望 CIDR 必须在 `main` 表中有符合有效性与竞争路由判定的受管路由，其他表的同网段路由不能满足校验；iKuai 两条端口分流的源排除、下一跳、协议、优先级与目的网段与计划一致。应删除的路由不再存在。iKuai 另查当前路由表，配置之外指向 mihomo 的内核残留路由记为“需处理”。
- NAT 阶段：需要显式免转换的期望 CIDR 被启用的受管规则目的网段覆盖；`not_required` 必须根据最新读取的配置再次成立。对本次实际管理的网段，`unknown` 在计划阶段阻止发布；因路由冲突明确跳过的网段不修改其路由或 NAT，并保留已有回流保护。
- DHCP DNS 阶段：目标网段的 DNS 列表与所选 OxiDNS 地址一致；写入及恢复均保留 DHCP 网关、地址池和租期等其他配置。
- 强制 DNS 阶段：清单中的对象全部存在、配置与回读一致、角色与计划一致；劫持规则之前没有其他启用的 53 端口 dstnat 规则。

RouterOS 驱动还逐项回读实际写入字段，并检查新 NAT 规则相对于指定规则的位置；扩充时保留的源地址、接口、协议等条件也纳入这层检查。

这些校验是配置回读，不包含 DNS 解析、代理实际访问、DNS 环路或真实客户端 IP 的完整流量验收。

### 6.4 回滚与结果

只撤销本次操作涉及的对象，不恢复整机备份。发布日志和回滚日志分别记录每项成功或失败；撤销请求也可能因设备离线、权限或接口错误失败。界面会区分发布完成、已撤销已完成变更、回滚未完成，不能把发布失败一律显示成“已回滚”。

回滚目前没有完整的并发修改冲突检测；计划指纹也不等同于锁定设备状态。发布期间应避免同时手动修改计划涉及的对象。

## 7. 页面与接口

配置空间下的“上游路由”页面提供：

- 路由器新增、编辑、删除；删除只移除 ConfigFlow 接入记录，不修改设备；仍有策略归属记录时须先成功发布撤回，否则拒绝删除。
- 每台路由器可选“自动配置回流”，默认关闭；关闭保留已有规则。保存修改后清除该路由器的旧报告和发布预览，重新读取后再发布。
- 选择 OxiDNS Agent 下发 DHCP DNS，默认不关联；报告显示未关联、已同步、待更新或待确认，预览包含目标网段与完整 DNS 列表变更，并提示终端续租后生效。
- 连接探测、版本和连接状态展示。
- “IPv4 转发”列：显示每台路由器代理网关（Mihomo Agent）的转发状态（已开启并持久化、已开启未持久化、未开启、需更新 Agent、离线、Docker 部署等）；未持久化时可确认后一键开启并持久化，写入 `/etc/sysctl.d/99-configflow-aio-forward.conf` 并注册 Agent 启动前检查，不修改核心配置、不重启服务。同机安装需 Agent `1.8.40-go`，单独安装需 `1.8.41-go`。该列独立读取，不阻塞路由器列表。
- 独立“管理路由”入口：读取设备实际路由，添加、编辑、启停或删除单条普通静态路由，预览确认后写入。
- 代理路由、NAT 免转换、mihomo 回流状态的差异报告；显示已同步、可接管、冲突、缺失、多余、无需免转换和待确认项。NAT 的说明栏展示出口与源 NAT 判定依据；无需免转换不计为缺失，证据不足时显示待确认。
- 发布预览、阻塞与警告提示、确认发布、逐阶段执行与回滚结果。

后端提供 `/api/routers` 的列表和新增，`/api/routers/<id>` 的编辑和删除，以及对应的 `/probe`、`/report`、`/plan`、`/apply`。独立路由管理使用 `/routes`、`/routes/plan`、`/routes/apply`。代理网关的 IPv4 转发使用 `GET/POST /api/routers/gateway-forwarding`（POST 只接受 `{agent_id}`，且该 Agent 须是当前配置空间某台路由器的代理网关）。

### 7.1 ROS 远程规则自动同步

在路由器行点击「规则同步」。首次先手动预览并成功发布一次，再开启自动同步；已建立基准时也可以先开关后按需发布。旧部署没有新版本的同步基准，需要重新手动预览发布，即使计划没有变更。开关默认关闭，关闭只停止后续检查，不撤销已下发对象。

后台按设定间隔拉取已选规则集的远程内容，同一轮复用同一下载来源；仅更新受管目的地址列表和登记过的静态路由。不自动接管同名、同网段或带 `cf` 备注但未登记的对象；不自动改变来源、网关、NAT、DHCP DNS 或 Agent 回流设置。若新网段需要额外 NAT 或回流操作，暂停并要求手动预览发布。多个规则集共用的目的 IP 按合并后的期望状态保留。

规则解析区分公网 IPv4、域名和其他条目。`classical` 允许 IP 与域名混合，域名不解析成 IP 下发；`ipcidr` 混入域名或无效行时停止。每个规则集分别比较有效 IPv4 数量，原来非零变为零时保留设备原状态；HTML 错误页、空内容、损坏的 YAML、未知规则类型也不能当成删除指令。IPv6、私网和其他非目的 IP 条目不生成主路由规则。

下载失败保留旧内容，下个周期可重试。格式异常、设置变化、外部对象改动或写入失败会暂停；先在规则仓库核对并更新缓存，再手动预览发布以重新建立基准。写入新增项后再移除旧项，回读校验失败逆序补偿；补偿可能产生新的 ROS 对象 ID，会保留更新后的归属记录。异常退出留下的执行中记录要求人工核对，不盲目重放。整个过程不代替真实网络连通性验收。

页面显示最近检查、内容更新时间、ROS 同步时间、增删数量、分类计数及读取/已同步版本。「立即同步」为异步任务；GET/PUT/POST `/api/routers/<id>/rule-sync` 分别查询、保存开关与间隔、启动任务，均鉴权并按配置空间隔离。任务与手动发布/单条路由写入共享设备连接锁。

运行记录存储在数据目录的 `router-rule-sync/`，只保留当前基准和最近结果，不保存凭据或下载原文，不作为历史备份；检查结果不会增加配置版本。下载限制为单文件 4 MiB、每台路由器内容总量 16 MiB、最多 128 个规则集、单文件 100000 条及有效 IPv4 合计 20000 条，超出时暂停并使用手动发布。轮次下载缓存最多 16 MiB，结束即释放。标准服务进程启动一个定时线程，多进程调度由文件锁限制；直接嵌入 Flask 时需显式调用 `start_loop()`。

ROS 回读成功后才更新本次下载的共享缓存。Mihomo/OxiDNS 的订阅刷新与 ROS 发布并非跨设备原子事务；其他入口也可能刷新缓存，页面的 ROS 版本不声称其他设备已加载相同版本。缓存写入失败会显示失败/暂停，已确认成功的 ROS 状态仍有记录。

## 8. 使用约束

- RouterOS 管理地址支持 HTTP 和 HTTPS：HTTPS 需要 RouterOS 7.1+ 并启用 `www-ssl`，HTTP 需要 7.9+ 并启用 `www`。两种驱动默认校验 HTTPS 证书，可在接入配置中调整；HTTP 不涉及证书校验。
- RouterOS 发布账号需要 `api`、`rest-api`、`read`、`write`；iKuai 需要管理员账号。添加或编辑 RouterOS 时可展开账号权限说明，按 WinBox 的 System → Users / Groups 设置专用账号和用户组。权限不足时，连接或发布错误会提供设置步骤；原始 REST 权限错误仍保留以便排查。
- 代理网段来源于 fake-ip 和显式选择的规则集，避免把全部规则集一律路由给 mihomo。
- 当前新增 NAT 源范围按 mihomo 地址的 `/24` 推导。多 LAN 网段、非 `/24` 拓扑尚无专用配置入口。
- 自动化测试覆盖 API/驱动与发布逻辑，不代替真实 RouterOS 或 iKuai 的网络连通性验收。

## 旧版无归属回流状态的处理

仅记录规格、没有可靠 `ownership` 清单的旧版 `return-routing.json` 无法证明内核对象归 ConfigFlow 独占。表名、链名、规则注释或与旧规格相同的内容都不能替代归属证据：其他程序可能保留这些名称和注释，同时修改规则表达式、链 hook 或策略。

Agent 启动时不自动迁移这类状态，无论 `active` 是否为真，都保留原 journal 和全部内核资源，不删除或替换 `configflow_return` 表、不交换策略规则、不删除旧路由，也不改旧备份或启动脚本。即使旧资源已经缺失，也不凭旧规格自动重建；需要先人工核实资源归属和残留状态。

自动分配仅适用于没有既有管理状态且能够证明目标资源空闲的首次发布，或复用已经验证的受管 journal。无 owner、未完成事务和外部漂移不会因自动分配而获得迁移或删除其他程序规则的权限。

## ICMP 重定向（Agent 1.8.9）

回流把回包强制送回主路由后，旁路网关从同一网卡收发转发流量时内核会向客户端发 ICMP 重定向，引导客户端绕过主路由。回流生效时 Agent 把 `net.ipv4.conf.{all,<LAN 网卡>}.send_redirects` 设为 0，并在状态文件 `send_redirects` 中记录首次修改前的原值；撤销回流时按记录恢复。Agent 重启跳过重放时也会重新确认该设置。写入失败只记日志，不影响发布结果。这不是归属资源，不参与归属校验。
