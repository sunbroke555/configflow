# Health-check advanced settings

## Scope and defaults
- Group checks and provider checks are independent. Matching their intervals is not required; 60 seconds is an application creation default, not an availability guarantee.
- New `url-test`, `fallback`, and `load-balance` groups: HTTPS Gstatic `generate_204`, interval 60 seconds, timeout 5000 milliseconds, lazy false, expected-status `204`. Only `url-test` receives tolerance 50 milliseconds.
- New shared subscriptions/aggregations: `health_check` with enable true, HTTPS Gstatic, interval 300 seconds, timeout 5000 milliseconds, lazy true, expected-status `204`.
- Existing records are not migrated. A source without `health_check` uses HTTPS Gstatic by default (or preserves its explicit legacy `health_check_url`), interval 300, lazy true, enable true, and omits timeout/status. Merely opening/saving a legacy source without changing its health fields does not opt it in. Editing a source's advanced controls opts it into the explicit object and its missing-field defaults. In an explicit object, clearing timeout or choosing “未设置” for lazy/enable keeps those keys absent through subsequent edits, save and reopen; generation supplies timeout5000/lazytrue/enabletrue without writing them back. Explicit false remains false. The editable model is not merged with defaults on each keystroke.
- Existing group fields retain explicit false values; absent fields remain absent. Legacy generator behavior (`url-test` lazy true/tolerance100) remains for unconfigured records. Only a final effective `url-test` group emits tolerance; other effective types omit it, including stale stored values. Type changes remove only fields inapplicable to the new type (for example tolerance on fallback); applicable settings are retained.

## Group update contract (REST and actual MCP)
The strategy-group page offers **批量测速地址** for selected ordinary `url-test`, `fallback`, and `load-balance` groups in the current profile, including disabled groups. `PUT /api/proxy-groups/batch-health-url` accepts `{ids: [...], url: "https://..."}` and updates only their URLs in one transaction. IDs must be nonempty, unique strings; any missing ID, unsupported type, follow group, or invalid URL rejects the entire batch. Follow groups use their source group's settings. Other health fields and unsaved source/regex drafts are retained. Existing explicit URLs are not migrated; generation/publication is required for devices to use saved changes.

`PUT /api/proxy-groups/{id}` and `manage_proxy_group(action="update")` are **partial merges**, including when `type` is supplied or unchanged. Omission never selects replacement mode. The MCP wrapper sends the partial patch directly; merging occurs against fresh transactional storage. Old clients remain partial clients.

To clear optional health fields, send `delete_fields: ["timeout", "lazy"]` alongside any edits. This is update-only metadata, never persisted. It accepts only unique names from `url`, `interval`, `timeout`, `lazy`, `expected-status`, `tolerance`; a field cannot be both assigned and deleted. Invalid operations are rejected atomically. Explicit deletions also win over creation defaults when a partial update changes a previously non-health group into a health type. The full group editor sends this list only for previously explicit fields the user clears; unrelated edits do not erase or materialize fields. Provider nested objects retain their separate existing merge/edit contract.

## Final managed candidate contract
Create and update validate the **final merged effective source group** with the same membership resolver used by generation. Managed sources are manual nodes (including explicit DIRECT/REJECT), enabled shared subscriptions, enabled shared aggregations, and enabled profile group references. Legacy `source: node` / `source: strategy` ID-based `proxies` are resolved only when named managed source lists are empty. Follow uses an enabled ordinary source group with actual consumed membership; chained follow is not supported by this generator. An ordinary group with direct followers cannot become a follow group or a chain source; target updates validate the affected direct followers against the final transactional group list. Target deletion/disable retains the existing reference guard. Rejection leaves every group unchanged; this does not introduce recursive follow.

Optional `regex` and `aggregation_regex` accept strings or null. Null/empty means no filter, preserving legacy generation for ordinary and follow groups. New writes of other types return controlled 400 errors before persistence. The renderer does not impose new strict string contracts on legacy stored records.

Nonempty `proxies_order` is precise node/group ordering, not an alternate source inventory. Every item must be exactly `{type,id}`, where type is `node`, `strategy`, or `aggregation`; IDs must belong to the corresponding selected source. Every selected manual node/group must appear once, duplicate items are rejected. Subscription providers are consumed through `subscriptions`, never through subscription ordering items; selected aggregations are providers even when absent from ordering. Raw `use`, `include_all`, `include-all`, and untyped `proxies` do not make an empty managed group valid; no support for these engine flags is added.

A newly created group cannot be empty. An effective valid existing group cannot be changed to empty. An already-persisted legacy empty group remains readable/generatable and accepts unrelated edits only with its source fields unchanged; no implicit DIRECT is inserted. A legacy empty group made valid is thereafter governed by the valid-group rule. Rejected API/MCP writes preserve the exact persisted group list across repository reopening.

`group_candidates.py` contains one source-precedence/order resolver and one consumed-membership renderer; routes validate against those outputs, and ordinary/follow generation calls the same renderer. Generation defaults remain separate from editable raw state. In particular provider `{interval:321}` and `{}` stay partial/empty after name-only save and reopen; absent controls show unset rather than false, and defaults are applied only in output.

## Units and validation
UI timeout is seconds, supporting millisecond precision; stored/API/MCP/YAML timeout and tolerance are milliseconds. Interval is seconds. The repository validates all shared/profile save/import/clone paths before committing: strict booleans; integer interval 1–86400, timeout 1–600000, tolerance 0–600000; credential-free HTTP(S) URLs; expected-status string `204` or slash-separated ranges such as `200-299/304` with ascending bounds in 100–599. Unknown provider health fields are rejected. No implicit boolean/string coercion.

The backend `/api/proxy-groups/health-defaults` is the frontend/default-metadata source. MCP `tools/list` advertises typed health fields, defaults, and the explicit deletion list; calls use the same API and repository validator. Invalid saves leave the dialog open with a visible message. Candidate and update contracts are defined above, not inferred from incidental payload fields.

## Shared impact and generation precedence
Provider settings belong only to shared subscription/aggregation resources, not profiles. The edit dialog lists referencing profiles (including transitive aggregation usage), warns that all consumers are affected, and saving does not push Agents. Strategy-group settings stay profile-scoped. No automatic synchronization between either layer; no new profile inheritance system.

Generated provider definitions use the shared source as truth, including `enable:false` and `lazy:false`. Custom-config `proxy-providers` health settings do not override managed sources: the generated provider collection replaces that section (existing generator precedence). Unrelated top-level custom configuration continues to be the starting template. Saving group configuration does not introduce a runtime-selected-proxy reset or change live controller choices.

## Native regression reproduction
The consumed-source matrix covers ordinary/follow groups, exact/no ordering, API/MCP creation, and built-in/manual-node/subscription/aggregation/group/legacy sources. Set `MIHOMO_BINARY` to the verified native executable (or install `mihomo` on PATH) to run its exact generated-YAML parser checks; these integration cases skip if no native executable is available. Synthetic custom configuration omits DNS fallback/GeoIP downloads, and provider cache fixtures contain synthetic localhost nodes; YAML output itself is not rewritten for parsing. Native parsing is not availability or traffic proof.

## Validation scope
The candidate is handed to one independent reviewer for targeted re-review of the reproduced blockers and affected callers, followed by the final full test/build and isolated acceptance gate. All known blockers and new regressions must be fixed; unrelated inherited defects are documented without expanding scope. There is no fixed review-round count; a material architecture/security-boundary change requires renewed comprehensive review.

The isolated staging evidence demonstrates real DOM edits, persistence/reopening, API rejection/readback, clone/export/import, two-profile shared impacts, actual subscription/aggregation provider rendering, and native Mihomo parsing of the exact generated YAML. It does not demonstrate real gateway outage failover or universal probe reachability. No production deployment, push, restart, Git commit or remote publication is performed by this candidate.
